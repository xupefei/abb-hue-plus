The custom add-on works, but we reverted to the built-in Hue integration context

We built and deployed a full custom free@home add-on (in addon-ts/), then the owner chose to go back to ABB's built-in Hue integration — it natively exposes Hue lights & groups with colour/temperature, which our add-on didn't. The add-on is deleted from the SysAP but preserved in the repo. Hue-side, all rooms have "Day Cycle" scenes; sensors/dimmers currently trigger Bright (with Bathroom + Staircase on a 07:00 Bright / 01:00 Rest night split).

Net: the integration itself is done and stable. Future work is enrichment (scene-triggering, colour, automation) — not a broken base.

01 What works

Proven against real hardware.

Custom Node/TS add-on on the SysAP solid

Built on ABB's @busch-jaeger/free-at-home ADK. Runs as a systemd container on-device (ws+unix:// socket, LAN-outage-proof). One virtual device per Hue room/zone; short-press → activate scene, hold → dim, two-way state sync via the Hue v2 event stream, auto-resync + force-sync button.

Fully scriptable add-on deploy automatable

Via /api/addon/v1: upload tar → create container → configure → start. Beats clicking through the app.

POST /api/addon/v1/rest/ref        (multipart field "data", type application/x-tar)
POST /api/addon/v1/rest/container  (body = add-on id as text/plain)
PUT  .../container/{id}/configuration
POST .../container/{id}/start      · logs: GET .../rest/journal/{id}

Hue-side org: per-room Day Cycle scenes done

build_day_cycles.py creates a 4-phase smart_scene (Concentrate → Bright → Relax → Rest, cool→warm) in every room. Brightness tuned per-room; Bathroom special-cased for a midnight shower.

Device renames via REST persists

POST /api/rest/device/{sysap}/{serial} with {"displayName":"…"} sticks. Same for channel display names.

02 What does not work

Platform walls. Don't re-litigate these — they're confirmed dead ends via the REST API.

Smooth live group dimming Zigbee-bound

Holding a dimmer to fade a Hue group is laggy / jumps in stages. Tried every path: streamed absolute setpoints, coalescing, single-in-flight, and dimming_delta (which is just relative ±N% steps, not a native ramp — dynamics.duration doesn't slow it). Root cause is the Zigbee group-command rate, not our code.

Writing channel parameters over REST app-only

e.g. the "switch-on: White vs Last Colour" setting (par0025: 1→White, 3→Last Colour). POST /api/rest/channel only accepts displayName — parameter writes are ignored. Same for room/floorplan assignment, sensor↔actuator pairing, scene editing.

Deleting virtual devices no endpoint

DELETE /virtualdevice → 404. And because we set setAutoConfirm(true), TTL expiry is disabled — orphaned Hue: switches never auto-vanish and must be removed by hand in the app.

The add-on "Log" tab in the app undocumented

Stays empty. console.log reaches the systemd journal (readable via the journal API) but not the app tab. setEnableLogging(true) only toggles the lib's internal error logging — no effect on the tab.

f@h-only name overrides for imported Hue lights syncs back

The built-in integration mirrors names from the bridge, so renaming an imported Hue light on the f@h side gets overwritten on next sync. Hue groups hold a f@h-side name; lights don't. (So "Hue light:" prefixes only stick if applied on the bridge — which pollutes the Hue app.)

03 Gotchas that will bite you

Hard-won landmines. Keep this list next to you.

Deleting a scene cascade-deletes its automations data loss

behavior_instances list dependees with level:critical including the scenes they recall. Delete a scene → the bridge silently removes every automation that recalled it. Audit dependees before mass-deleting scenes. This cost us the motion automations once.

Container stop/start does NOT reload code deploy

A container keeps running the code it was created with. To ship new code you must recreate it: stop → DELETE ref → upload → create → configure → start. And a back-to-back delete/create races ("Unable to checkout commit: File exists") — add ~4s pauses; if it half-creates and crash-loops, fully tear down and retry.

smart_scene quirks Hue v2

  • Tile renders only with ≥3 timeslots (2 = blank tile).
  • metadata.image settable only at POST, never PUT.
  • Sunset slot: write {"kind":"sunset"} with no time field — the bridge returns time:{0,0,0} on read but rejects it on write.
  • Only time and sunset kinds — no sunrise (that lives on the v1 Daylight sensor / behaviors).

Virtual-device identity & type duplicates

Native id must key on a stable identity (room/scene UUID), never the target scene — else changing what a switch triggers spawns a duplicate. And device type can't change on an existing native id (Switch→Dim needs an id salt). The SysAP assigns its own native serial; your chosen serial is just a handle — match your devices by interface: vdev:<user>@….

f@h dimmer sends noise runtime

It fires its cached brightness ~4ms after an ON (guard it, or it overrides the scene), and repeats the extreme value (1%/100%) while you hold at the end of range (dedup it). Its slider keeps its own setpoint, so a hold after a scene change ramps from a stale value.

Useful primitives reference

  • home_off — a Hue-Accessories action = whole-house off (cleaner than all_off scoped to bridge_home).
  • bridge_home grouped_light = all lights on the bridge.
  • Light powerup.preset = physical power-on behaviour (currently all powerfail/previous) — not the same as the f@h switch-on mode.
  • TTL minimum for a virtual device is >60s (180 works).

04 Worth trying next

Ranked by value ÷ effort.

The XMPP-RPC channel high valueeffort: high

The web UI does all the things REST can't — room/floorplan assignment, pairing, channel params, scene edits — over XMPP to mrha@busch-jaeger.de/rpc, wrapped in RemoteInterface.cryptMessage (encrypted payload). This is the real "full-config" API. Automating it means implementing the encrypted XMPP/SASL handshake (port 5222) + the internal RPC vocabulary.

Start from community libs (freeathome-api and similar) that already implement the handshake — don't reinvent the crypto.

Add colour / temperature to the add-on high valueeffort: med

Our add-on used a brightness-only DimActuator (func 12). The official integration uses a colour-capable actuator (func 2E) exposing CT + RGB. The ADK library has colour-capable channel types — adopting one closes the biggest gap that drove the revert.

Per-light dimming instead of per-group experimenteffort: med

Group dimming hits the Zigbee broadcast limit. Driving individual lights may fade smoother (at the cost of more virtual devices and fan-out writes). Worth a spike before concluding smooth dimming is impossible.

Crack the app Log tab nice-to-haveeffort: low–med

SSH into the SysAP (port 22 open; needs the app-shown SSH password, not the local-API one) and read a reference ABB add-on to see how it feeds the Log tab — or check the node-free-at-home wiki. Purely a debugging-UX win.

05 Fast reference

Copy-paste starting points.

Talk to the Hue bridge

KEY=$(python3 -c "import json;print(json.load(open('.hue-credentials.json'))['application_key'])")
curl -sk https://BRIDGE_IP/clip/v2/resource/scene -H "hue-application-key: $KEY"

Talk to free@home (local API)

curl -sk -u "$USER:$PASS" https://SYSAP_IP/fhapi/v1/api/rest/configuration
# local dev for the add-on: FREEATHOME_BASE_URL must be http:// (not https)

Build the add-on

cd addon-ts && npm install && npm run build && npm run pack   # -> -.tar

This document plus the repo source (addon-ts/, src/, build_day_cycles.py) is the complete context — everything here was distilled from building and testing against the real hardware.
